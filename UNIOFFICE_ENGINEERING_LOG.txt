CHANGES MADE
==============================================================================

1. Missions are planned and queued on the server in one step.

   Problem, reproduced rather than assumed:
     The room started a mission with two browser requests: POST /plan, held
     open for the whole plan (measured 102-118 s), then POST /execute. If
     the browser did not complete the second request - tab closed, laptop
     asleep, connection dropped, a proxy giving up on a long request - the
     mission was left planned, status "queued", with ZERO execution jobs.
     The worker only claims jobs, so nothing would ever run it, while the
     status said it was waiting. Demonstrated on mission 3760ff44: planned,
     3 tasks pending, 0 jobs.

   Fix:
     - apps/api/src/mission-launcher.ts: plans then queues on the server,
       tracks launches per mission so one mission is never planned twice.
     - POST /work/:id/launch: same permission as running a mission
       (missions.operate, re-checked against current membership). Answers
       202 at once. 409 if already planning or already planned. 503 if the
       server has no launcher.
     - POST /work/:id/plan now refuses while a launch is in flight, so the
       older route cannot start a second plan beside it.
     - The room's autostart and replan-retry call launch instead of
       plan-then-execute.
     - Nothing else changed: planning, queueing, the worker, the queue
       schema and the database are untouched. No migration.

   This also removes the Cloudflare timeout exposure entirely: no request
   is now held open for longer than a couple of seconds.

2. A cancelled mission can no longer be revived by a launch.

   Found live, not in review: a permission probe cancelled a mission a
   moment after launching it. The mission ran to completion anyway.

   Cause: two stale whole-row writes. The cancel landed in the gap before
   the background plan marked the mission as planning, and the plan then
   wrote its own copy over the cancellation, finished, and queued it.

   Fix, in two commits:
     a) 0382397 - the launch route marks the mission as planning with a
        conditional write (WorkRepository.transitionStatus: update ... where
        status = 'queued') BEFORE answering 202. A cancel that got there
        first wins (launch gets 409); one that arrives after is refused,
        because cancelling a mission that is actively planning was already
        refused.
     b) 85705a5 - planWork no longer rewrites a mission a launch already
        marked as planning, and re-reads the mission after the model
        returns: if it was cancelled meanwhile, no steps are created and it
        is not put back to waiting. The launcher queues only a mission the
        plan left waiting.

   (a) alone was NOT enough. Re-running the race on 0382397 and waiting for
   the plans to finish showed a mission reported cancelled that still went
   on to complete. (b) closes it: re-running on 85705a5, all three cancelled
   missions stayed cancelled with 0 tasks and 0 jobs, checked after their
   plans would have finished.

3. The live API now accepts the production web origin (local config only).

   The API's CORS allow-list comes from API_CORS_ORIGINS. It was not set in
   the local .env, so it defaulted to localhost only: every browser request
   from https://unioffice.pro would have been refused. Added to the local
   .env (not committed, never tracked):
     API_CORS_ORIGINS = https://unioffice.pro, https://www.unioffice.pro,
                        http://localhost:5173, http://127.0.0.1:5173
   The localhost entries stay because this machine is also the development
   machine. Verified through the public URL: unioffice.pro and www allowed;
   unioffice.online and an arbitrary origin get no CORS header.

4. A web test file no longer times out on a busy machine.

   The first final full run (`pnpm test --force`) failed 2 tests in
   apps/web/src/pages/TemplateMission.test.tsx: one timed out at 5078 ms
   against a 5000 ms limit, one missed the transient "Starting..." state.
   The same file passed 3/3 alone and the web suite passed 136/136 alone, so
   it was load, not a regression - but `pnpm test` is the gate, and it could
   fail at random. Cause: the shared helper typed ~66 characters key by key,
   and each keystroke re-rendered the whole template page. It now pastes the
   answers (still real user-event focus and input). No assertion changed.
   File time fell from ~4.6 s to ~1.9 s of test time; the full run then
   passed under the same load.
